统一研发知识架构

用一个入口承载游戏设计、客户端、服务器与跨端契约，同时通过知识空间隔离职责，通过唯一事实来源减少重复维护。

◷ 更新于 2026-10-10 ♙ Owner：技术委员会 ◉ 状态：已评审 ⌁ 12 个关联页面

设计目标

顶部负责切换知识边界，左侧负责模块定位，右侧负责当前页面阅读。跨端契约连接各研发领域，但不复制任何一方的实现。

游戏规则→ 契约→ 技术实现

知识空间

每个空间拥有独立左侧目录和负责人。搜索、术语、变更记录与关联关系保持全站统一。

SPACE 01

游戏领域

描述玩法目标、业务规则、数值公式和验收标准，回答“是什么、为什么”。

SPACE 02

客户端技术

描述界面、表现、资源、网络接入与平台适配，回答“客户端如何实现”。

SPACE 03

服务器技术

描述权威计算、存储、一致性、部署与容灾，回答“服务端如何保证正确”。

SPACE 04

跨端契约

统一管理协议、错误码、事件和配置 Schema，是各端之间的唯一连接层。

边界与归属

同一业务由多个团队共同完成时，按照“规则—契约—实现”拆分，而不是每个团队各写一套完整说明。

游戏领域拥有规则和数值，例如强化成功率、消耗规则和失败结果。
跨端契约拥有字段和传输语义，例如请求、响应、错误码以及版本兼容约束。
客户端拥有交互和表现，例如强化界面、动画、状态反馈和资源生命周期。
服务器拥有权威执行，例如资格校验、资源扣除、随机计算、事务和落库。
唯一事实来源

强化概率只在游戏领域文档定义；协议字段只在跨端契约定义。客户端和服务器页面通过关联链接引用，不复制原文。

目录结构

物理文件按知识空间隔离；全站公共内容只保留一份。页面地址保持稳定，目录改名不应破坏历史链接。

docs/ ├─ start/ # 首页与按角色开始 ├─ game-domain/ # 游戏领域 │ ├─ combat/ │ ├─ equipment/ │ └─ economy/ ├─ client/ # 客户端技术 │ ├─ onboarding/ │ ├─ framework/ │ └─ troubleshooting/ ├─ server/ # 服务器技术 │ ├─ onboarding/ │ ├─ infrastructure/ │ └─ operations/ ├─ contracts/ # 跨端契约 │ ├─ protocols/ │ ├─ errors/ │ └─ schemas/ ├─ shared/ # 公共知识 │ ├─ glossary/ │ ├─ workflow/ │ └─ adr/ └─ mkdocs.yml # 站点导航配置

避免文档冗余

一个概念，一个权威页面

为每个页面设置领域、Owner 和权威状态。其他页面只补充本领域上下文，并明确链接到权威页面。

可生成内容不手写

协议、RPC、配置结构和 API 参考应由 Protobuf、OpenAPI、Schema 或代码注释自动生成，人工文档重点解释设计意图和使用约束。

公共片段集中维护

环境地址、权限申请、Git 流程等内容进入公共知识。各新人指南组合阅读路径，不再重复粘贴操作步骤。

新人阅读路径

了解游戏与技术全景阅读项目术语、端到端链路和系统架构图。
选择岗位路线进入策划、客户端或服务器新人指南，完成本地环境搭建。
跟踪一条真实链路从游戏规则开始，经过协议，最终定位到客户端与服务器实现。
完成第一个任务修改、验证、提交并更新对应文档，完成知识闭环。

维护约定

业务变更必须同时检查规则、契约与实现文档。每个空间由领域 Owner 定期审阅；过期页面进入归档并保留跳转，不直接删除。
